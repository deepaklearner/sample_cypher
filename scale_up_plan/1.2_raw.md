Using `OFFSET` and `LIMIT` works for **small to medium datasets**, but given your size (`entitlement_master` = 8.8 million rows), it becomes **increasingly inefficient** as the `OFFSET` grows.

Let’s break this down and look at better options.

---

### ⚠️ Problem with OFFSET/LIMIT on Large Tables

The query:

```sql
SELECT * FROM entitlement_master
OFFSET 8000000 LIMIT 10000;
```

May seem harmless, but it forces the database to **scan and skip 8 million rows**, even though it only returns 10,000. As the offset increases, **query performance degrades rapidly**.

---

### ✅ Better Alternatives for Large-Scale Batching

#### ✅ Option 1: **Key-Based Pagination (Recommended)**

If your `entitlement_master` has a unique column like `id`, `created_at`, or even `ROW_NUMBER()`, use it for **"seek method" pagination**, which is much faster.

Example:

```sql
SELECT * FROM entitlement_master
WHERE id > {last_processed_id}
ORDER BY id
LIMIT 10000;
```

* Much faster than OFFSET
* Easy to resume from failure (store `last_processed_id`)
* Avoids duplicate or missing rows (as long as `id` is stable)

👉 If `entitlement_master` doesn’t have a numeric ID, you can:

* Use a **generated surrogate key** (e.g., row number)
* Use **composite key** (e.g., `(entitle_name, platform)` with lexicographic pagination)

---

#### ✅ Option 2: Materialize Row Numbers Once

If you can't change the schema, create a temporary or persistent table with row numbers:

```sql
CREATE TEMP TABLE entitlement_master_indexed AS
SELECT
  ROW_NUMBER() OVER (ORDER BY entitle_name, platform) AS row_num,
  *
FROM entitlement_master;
```

Then paginate efficiently using:

```sql
SELECT * FROM entitlement_master_indexed
WHERE row_num BETWEEN 100001 AND 110000;
```

* Much faster than OFFSET on original table
* Can still track progress via `row_num`

---

### 🧠 When is OFFSET OK?

You can continue using `OFFSET/LIMIT` *if*:

* You’re in **early stages** or testing
* Each batch is small (< 10k rows)
* You’re not offsetting beyond \~500k rows
* Your database can handle it (e.g., fast SSDs, indexed reads)

But for **8.8M+ rows**, you’ll want to **switch to key-based pagination** soon.

---

### 🛠️ How to Transition to Key-Based Pagination

1. Check if `entitlement_master` has a stable primary key (e.g., `id`, timestamp)
2. If not, create a materialized table with row numbers
3. Replace your `OFFSET` logic with a `WHERE key > last_key` clause
4. Track `last_key` in a metadata store (file, table, etc.)
5. Add `ORDER BY` to make batching deterministic

---

### 📌 TL;DR

| Approach         | Good For         | Performance (Large Tables) | Resume Support |
| ---------------- | ---------------- | -------------------------- | -------------- |
| `OFFSET + LIMIT` | Dev/testing      | ❌ Poor (after few 100k)    | ⚠️ Harder      |
| `WHERE id > ?`   | Production-scale | ✅ Excellent                | ✅ Easy         |
